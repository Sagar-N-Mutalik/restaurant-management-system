2. Deep Dive: The 7 Testing Methodologies Explained

Below is an exhaustive breakdown of each testing discipline, explaining its theoretical definition, why our project requires it, the underlying code implementation, and key takeaways for viva presentation.

Topic 1 Unit Testing (Component Level)

5 Tests • 100% Pass
Academic Definition (IEEE / ISTQB)

Unit testing is the process where individual units or components of a software system are tested in complete isolation from external subsystems (such as databases, file storage, or network layers). Its primary objective is to validate that each software component performs its internal algorithmic computation exactly as designed.

Why Selected for Smart Restaurant System?

In a restaurant billing system, pricing errors directly damage customer trust or revenue. We use Unit Testing to mathematically verify our PricingStrategy implementations (Normal 1.0x, Happy Hour 20% discount, VIP custom discount rate, and 18% GST calculation) and our MenuItemDecorator wrappers (stacking Extra Cheese and Bacon) in complete isolation.

Implementation Showcase
# restaurant/test_suites/test_unit.py
class PricingStrategyTests(SimpleTestCase):
def test_happy_hour_applies_twenty_percent_discount(self):
actual = HappyHourPricing().calculate_final_price(10)
self.assertEqual(actual, 8) # 20% off 10 = 8.0

def test_decorators_add_prices_and_descriptions(self):
item = MenuItemComponent(SimpleNamespace(name='Burger', price=10))
customized = AddBaconDecorator(ExtraCheeseDecorator(item))
self.assertEqual(customized.get_price(), 14) # 10 + 1.5 + 2.5
Viva Takeaway: "Unit tests do not touch the database or network, allowing all 5 tests to execute in under 4 milliseconds, providing rapid feedback during pricing modifications."

Topic 2 Integration Testing (Subsystem Level)

2 Tests • 100% Pass
Academic Definition

Integration testing evaluates the interfaces, communication protocols, and data persistence between integrated software modules. It uncovers interface bugs, transaction rollbacks, relational database mismatches, and asynchronous event delivery problems.

Why Selected for Smart Restaurant System?

While unit tests confirm that individual pricing classes work alone, integration testing proves that our OrderProcessingFacade coordinates Django ORM database persistence, table occupancy status mutations, and real-time Observer alerts (kitchen displays and waiters) in an atomic transaction.

Implementation Showcase
# restaurant/test_suites/test_integration.py
class OrderWorkflowIntegrationTests(TestCase):
def test_facade_persists_order_and_occupies_table(self):
result = self.facade.place_order(customer_name='Guest', ...)
order = Order.objects.get(pk=result['order_id'])
self.assertEqual(order.status, 'PREPARING')
self.assertTrue(self.table.is_occupied)
Viva Takeaway: "Integration testing verifies our Design Patterns in action with the Django database layer: placing an order mutates table state to occupied and broadcasts observer notifications."

Topic 3 Black-Box Testing (Specification / Contract)

5 Tests • 100% Pass
Academic Definition

Black-box testing (functional/specification testing) examines software functionality without knowing or inspecting internal source code or architecture. The system is evaluated entirely based on inputs, outputs, and requirements specifications.

Why Selected for Smart Restaurant System?

Customers ordering via QR codes and third-party dashboard clients interact solely through HTTP REST endpoints. Black-box testing ensures that submitting an order via POST /api/order returns standard HTTP 201 Created, rejects GET requests with HTTP 405 Method Not Allowed, and securely serves formatted Excel reports with accurate headers.

Implementation Showcase
# restaurant/test_suites/test_black_box.py
class PublicHttpContractTests(TestCase):
def test_order_api_creates_order_and_returns_documented_payload(self):
res = self.client.post('/api/order', data=json.dumps({...}), ...)
self.assertEqual(res.status_code, 201)
self.assertTrue(res.json()['success'])

def test_order_api_rejects_get_requests(self):
res = self.client.get('/api/order')
self.assertEqual(res.status_code, 405)
Viva Takeaway: "Black-box tests validate our external REST API contract without needing to know internal model details, assuring client-server stability."

Topic 4 White-Box Testing (Structural / Coverage)

3 Tests • 100% Pass
Academic Definition

White-box testing (glass-box or structural testing) examines internal code structures, branch decision logic, exception conditions, and statements. It enables objective calculation of code coverage metrics.

Why Selected for Smart Restaurant System?

In addition to sunny-day workflows, software must handle edge conditions gracefully. Our white-box suite tests that SimpleMenuFactory raises ValueError with clear error text on unknown menu categories, and verifies that completing non-existent order IDs returns False without unhandled server exceptions.

Implementation Showcase
# restaurant/test_suites/test_white_box.py
class InternalBranchTests(TestCase):
def test_factory_rejects_unknown_item_category(self):
with self.assertRaisesRegex(ValueError, 'Unknown menu item category'):
SimpleMenuFactory.get_item('unknown', 'Mystery', 10)

def test_completing_unknown_order_returns_false(self):
actual = OrderProcessingFacade().complete_order(99999)
self.assertFalse(actual)
Viva Takeaway: "White-box tests verify internal defensive guard branches and statement coverage across models, patterns, and views."

Topic 5 Smoke Testing (Build Sanity Verification)

1 Test (5 Routes) • 100% Pass
Academic Definition

Smoke testing (Build Acceptance Testing) is a rapid sanity check executed immediately after building software. It tests whether critical baseline functions and primary entry points respond without fatal crashes before running time-consuming suites.

Why Selected for Smart Restaurant System?

In continuous deployment, broken HTML template tags, unimported view functions, or missing URL parameters can break customer pages. Our smoke test exercises all 5 primary application routes (Landing page, Staff Dashboard, Test Hub, Table Menu, and Payment page) ensuring each returns HTTP 200 OK.

Implementation Showcase
# restaurant/test_suites/test_smoke.py
class MainPageSmokeTests(TestCase):
def test_main_pages_load(self):
routes = (reverse('index'), reverse('staff_dashboard'), ...)
for route in routes:
self.assertEqual(self.client.get(route).status_code, 200)
Viva Takeaway: "Smoke testing acts as our rapid gatekeeper; if core routes do not return 200, the deployment is aborted immediately."

Topic 6 Regression Testing (Defect Prevention)

3 Tests • 100% Pass
Academic Definition

Regression testing ensures that code modifications, bug fixes, or new feature additions do not inadvertently break pre-existing functionalities or introduce unintended side effects into other modules.

Why Selected for Smart Restaurant System?

As we added cart order features and discount strategies, regression tests guaranteed that sending malformed JSON strings returns HTTP 400 Bad Request instead of a server 500 crash, order ready transitions update database states reliably, and payment calls on empty tables do not mutate table locks.

Implementation Showcase
# restaurant/test_suites/test_regression.py
class OrderRegressionTests(TestCase):
def test_invalid_json_order_request_returns_bad_request(self):
res = self.client.post('/api/order', data='{invalid', ...)
self.assertEqual(res.status_code, 400)
self.assertFalse(res.json()['success'])
Viva Takeaway: "Regression tests ensure that malformed client payloads and edge transitions are handled defensively without system breakdown."

Topic 7 Performance Testing (Latency & Scalability)

2 Tests • 100% Pass
Academic Definition

Performance testing is a non-functional testing technique that evaluates software responsiveness, execution speed, resource utilization, and throughput under specified workload bounds.

Why Selected for Smart Restaurant System?

During peak dining hours, hundreds of customer tables calculate bills and view menus concurrently. Performance testing proves that our Strategy pricing algorithm calculates 5,000 prices in under 0.02 seconds (budget: <2.0s), and repeated web page dispatches complete within sub-second thresholds.

Implementation Showcase
# restaurant/test_suites/test_performance.py
class BoundedPerformanceTests(TestCase):
def test_pricing_calculations_complete_within_budget(self):
started_at = perf_counter()
for _ in range(5000): strategy.calculate_final_price(12.5)
elapsed = perf_counter() - started_at
self.assertLess(elapsed, 2.0) # Actual: ~0.015s
Viva Takeaway: "Performance tests establish O(1) mathematical complexity of our design pattern algorithms under high computational load."

5. Examiner Viva Preparation & Defense Q&A

High-yield academic questions commonly asked by professors, lecturers, and external examiners during project defenses, accompanied by technical model answers.

Answer: Unit testing isolates individual classes (like NormalPricing, HappyHourPricing, or ExtraCheeseDecorator) without touching external resources like databases or HTTP dispatchers. In contrast, Integration testing connects multiple subsystems together—specifically validating that our OrderProcessingFacade coordinates Django ORM database persistence, table occupancy mutations, and Observer kitchen notifications in one atomic workflow.

Answer: External clients such as customer mobile browsers and QR code scanners do not have access to Django's internal functions or database schemas. Black-box testing validates that from an external perspective, the system strictly respects standard HTTP protocols: returning 201 Created with a valid JSON contract on order submission, returning 405 Method Not Allowed when an invalid HTTP method is attempted, and serving compliant Excel files.

Answer: Smoke testing (Build Acceptance Testing) is a rapid sanity check that verifies whether the core infrastructure of the application is operating before executing deeper regression tests. In our project, it verifies that all 5 essential routes (Home landing, Staff dashboard, Test hub, Menu page, and Bill payment page) return HTTP 200 OK without unhandled template or routing exceptions.

Answer: Running automated tests against live restaurant data is dangerous because test transactions could alter active customer bills, accidentally occupy reserved tables, or skew financial auditing records. Django's test runner dynamically creates an isolated in-memory SQLite database for the duration of the test run and safely tears it down afterward, guaranteeing zero live data mutation and idempotent test repeatability.

Answer: We mapped tests directly to each pattern:
  • Strategy Pattern: Unit tests verify that swapping pricing strategies dynamically computes standard, happy-hour (20% off), and VIP discounts with exact mathematical precision.
  • Decorator Pattern: Unit tests verify dynamic runtime price stacking and description formatting of toppings without subclass explosion.
  • Facade Pattern: Integration tests prove that a single method call simplifies order persistence, table locking, and observer notifications.
  • Observer Pattern: Integration tests assert that changing an order state automatically triggers alerts to kitchen displays and waiters.
  • Factory Pattern: White-box tests verify category validation and exception throwing on unsupported food items.
